# litv → LITTO：制作机制与移植取舍

分析日期：2026-10-11。litv 基线：`dd12ed24fe1292824cd011208f23c259caedadfe`；LITTO HEAD：`612b065054cea001b6b7cf2c156e157cb3c69a98`，同时检查当前工作区源码。已有未提交改动保持原样。

本轮是源码分析与无副作用的目录/计划结构统计，没有调用付费模型，没有运行两套系统的真实成片对照，没有修改生产逻辑。代码存在、链路连通、输出质量分别判断。下文的移植方案尚未实施。

## 1. 先定义问题：降低完成一部可修改作品的总成本

用户最终需要的是符合创作意图、可继续修改、可实际交付的作品。Skill 数量、提示词长度、节点数量和生成成功率都只是中间指标。

可以用一个决策模型解释投入优先级：总成本包括生成成本、等待成本、用户决策成本，以及失败后重做受影响成果的期望成本。这里没有实测金额，不能据此宣称节省某个百分比。

- 定脸先于全身和镜头：尽早消除会传播到大量成果的身份不确定性。
- 试片先于量产：用一段真实运动验证模型能否完成高风险动作，避免把同一失败复制到全片。
- 产品原图禁止被重生成替代：保护事实来源，而非仅提高图片相似度。
- 修改后复核下游：防止“文件还在”被误认为“结果仍适用于当前方案”。

因此值得移植的最小单位是“一个真实风险对应的输入、依赖、执行与验收机制”。风格名称可以是入口，但不是能力本身。

## 2. 两边的 Skill 实际不在同一层

litv 有两套不同的对象：

1. 自由工作流中的 Skill：`workflow.mjs` 的默认文本指令或模板，由 `skill` 节点消费。
2. 制作型 Skill：`recipes.mjs` 的目录记录、`recipe-blueprints.mjs`/`extended-recipes.mjs` 的计划结构、`director.mjs` 的文档阶段，以及 `production.mjs` 的任务执行与人工验收。

第二类不是一个可以复制进 LITTO 技能目录就完整生效的 Markdown 文件。它包含了状态机和业务代码。litv 自身也说明其实现依据可见流程独立编写，不能当作原站私有 Skill 的完整恢复。

LITTO 的文件技能经 `loadAgentSkills` 提供给 Agent；Agent 再调用 `productionSpec`、媒体生成、审批与剪辑工具。工具背后已有强制执行的领域规则。因此也不能把 LITTO 简化为“只有提示词”。

| 层级 | litv 当前实现 | LITTO 当前实现 | 对迁移的含义 |
| --- | --- | --- | --- |
| 任务入口 | 80 项具名制作入口与路径选项 | 首页故事、广告、MV 等入口，按需文件技能 | 可以借鉴细分任务的发现方式，不必复制数量 |
| 方法知识 | 阶段要求、风格规则、计划提示词 | 技能正文、按需参考、导演与连续性方法 | 只补真正缺少的方法 |
| 计划 | 带 role、referenceIds 等的 recipe items | Story/SceneList、Asset、Sequence、ShotSpec | 转成已有领域对象，不能并存两套真相 |
| 执行 | makeTasks 生成任务依赖，readyTask 阻止越过上游 | 编译、能力检查、指纹、主帧、Job 与审批 | 优先保留 LITTO 的细粒度校验 |
| 反馈 | 手动 checklist、五帧视觉检查、历史文件 | QC 证据、实际末态、工作版与正式验收、成片检查 | 迁移时不能把“点过验收”提升为质量事实 |
| 修改 | 沿依赖撤销验收，保留旧文件 | 规格/参考/状态指纹、版本、剪辑指纹 | 需要补可解释的影响范围，而非替换机制 |

证据：[litv 工作流](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/workflow.mjs)、[制作执行器](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/production.mjs)、[LITTO 技能加载](../apps/server/src/agent/skills/index.ts)、[制片工具入口](../packages/tools/mediaGeneration/src/index.ts)。

## 3. 数量拆解：80 个入口代表多少机制

通过 Bun 直接导入 litv 的 `recipes`/`blankPlan`，遍历全部默认计划；按每项的 role、referenceIds、blockingVideoItemIds、sourceOnly 序列归并，得到：

- 80 个制作入口。
- 20 个旧专项条目，60 个扩展条目；扩展条目分布在 24 个 family。
- 在上述统计口径下有 39 种默认计划结构。
- 19 个入口共享一组默认结构；另有 9 个广告入口共享一组默认结构。

这不意味着其创作内容等价：统计有意排除了提示词、风格要求、时长、具体参数与非默认分支，也没有把计划展开为最终任务图。它只证明“80 个入口”不能当作“80 套独立技术能力”。例如人物/场景锚点加多镜头的结构，可以承载许多不同美术风格。

对 LITTO 更合理的拆分是：任务配方决定先做什么；风格资料决定怎么表达；模型能力决定实际能执行什么。不要把三者绑定成每个风格一套后端。

## 4. 追到执行边界后的关键差异

### 4.1 DAG 的价值是让前置条件可执行

litv 的 `makeTasks` 将计划展开：shot 通常成为图片任务与视频任务，choice 要先裁出选中格，grid 产生拆格任务，音频先切片，再供视频引用。`readyTask` 要求所有上游任务 approved 才允许继续。服务器检查与前端禁用按钮同时存在。

例如选角三视图要求脸图与全身图两个上游，`validatePlan` 不允许移除必要引用。收益来自“错误顺序无法轻易发生”，不是来自“定脸”这个词。

但 litv 把大部分依赖都放进 `depends`，而执行时又从 depends 收集媒体。它用 `blockingVideoItemIds` 补充“只阻塞，不一定提供参考”的情况。这透露出迁移时必须区分三种关系：

- 数据关系：下一步实际需要哪张图、哪段声音。
- 验收关系：下一步必须等哪项风险验证通过。
- 连续性关系：下一镜继承哪些实际状态。

三者不能都解释成画布连线。LITTO 已有 reference_bindings、QC 和 shot_states，应该复用这些语义，不把所有上游文件无差别塞进生成请求。

### 4.2 LITTO 已经有强制编译链，不能重新补造

当前账号制片路径为：

`productionSpec 保存规格 → prepareShot / prepareWorkspaceShot → compileShot → requireCompiledInputs → 指纹比对 → enqueueWorkspaceMedia → executeMediaJob → 生成结果 → Keyframe/Take → 检查与采用 → 剪辑/导出`

关键事实：

- `enqueueMedia` 对带 shotId 的请求重新准备规格，要求 productionFingerprint 一致，使用编译结果替换自由 prompt。
- `prepareWorkspaceShot` 的视频路径要求有效且检查过的主关键帧；不能仅有一张图片路径。
- `requireCompiledInputs` 拒绝无法发送的 LOCK 参考以及未完成的创作准备。
- `executeMediaJob` 使用实际编译输入重建图片、音频、视频、首尾帧请求，不只是把媒体 ID 写进文案。
- 编译器明确区分原生首帧和普通参考；用途/权重的记录不代表供应商承诺像素锁定。

普通独立媒体生成仍有不绑定 shotId 的路径，因此上述保证有明确适用边界，不宜宣传为所有生成入口无条件享有。

旧 `prdAudit.md` 含历史上“尚未接通”的记录，不能直接作为当前缺口。本轮判断以现行源码为准，也未据此认定全部 PRD 已完成。

证据：[jobs](../apps/server/src/utils/media/jobs.ts)、[workspaceMedia](../cloud/src/workspaceMedia.ts)、[compiler](../cloud/src/domain/compiler.ts)、[lifecycle](../cloud/src/domain/lifecycle.ts)。

### 4.3 静态样镜与动态试片验证的是不同风险

litv 的 canary 配方先产生关键镜头视频，并通过 blockingVideoItemIds 阻塞后续制作。它回答的是：这类动作、运动或表演在当前生成条件下是否成立。

LITTO 的 `adReadiness` 已要求指定样镜的主关键帧、视觉检查、当前指纹和 QC 全部匹配；编译器也会把已采用样镜作为后续图片 LOOK 参考。这个机制比一句“先做小样”更强，但其核心验收对象是 keyframe。

静帧可以证明产品外形、光色和材质在该帧成立，不能证明人物拿起产品、开盖、说话及动作衔接成立。LITTO 的技能已有“先验证一段”指导，但本轮没有在已检查制片路径中发现与 litv canary 对应的通用跨镜头视频前置门禁。

值得补的是动态风险验证：仅高风险方案选择一个代表镜头，采用真实视频后才开放受它影响的批次。应复用 Take/QC/指纹；参考视频是否送入模型另行决定，不能为了设置门禁就把它变成所有镜头的运动参考。试片不强制 4 秒，应按动作完整性和实际模型能力定长。

### 4.4 版本有效性比任务显示 completed 更重要

litv 的 `invalidateProduction` 沿 depends 传播，把相关任务退回 pending、移除检查和验收，旧 assetId 保留并标 stale。优点是修改影响可见，旧文件可找回；全局 notes/continuity 改动以及部分导演文档修订会触发较大范围失效，粒度较粗。

LITTO 的 `shotFingerprint` 包含镜头、世界、Look、资产、绑定、继承状态等；静帧指纹有意排除音乐时间线及前镜 Take ID 的直接变化。`requireReviewed` 核对当前指纹与媒体，成片另有 sequenceFingerprint。这个设计已经具备按内容有效性判断的基础。

不过指纹不等于完美的最小影响分析：当前也包含较宽的世界/Look 记录；不能声称所有无关编辑都不会失效。它也不天然给用户解释“是哪一项变了”。

可借鉴的是 litv 的修改反馈：明确展示需重新检查、需重新编译、需重新生成的不同范围。三者不能合并为自动重跑，更不能抹掉旧文件。

证据：[litv 修改传播](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/production-structure.mjs)、[LITTO 指纹](../cloud/src/domain/realism.ts)、[状态继承](../cloud/src/domain/state.ts)、[成片有效性](../cloud/src/domain/finalQuality.ts)。

### 4.5 UGC 的“多版本”是实验关系，不是连续剧情

litv 的出海 UGC 配方有主版、只改变开场的版本、只改变行动号召的版本；任务构造明确排除把这些视频自动拼成一条。

背后的原则是控制变量：在主体、产品、证据、其他文案尽量相同的条件下改变一个因素，后续反馈才较容易解释。生成模型仍有随机变化，所以不能仅凭同一 prompt 或 seed 就宣称构成严格因果实验。

LITTO 有广告策略、产品权威参考、情绪弧线、镜头与剪辑；本轮未在当前广告规格中找到明确的变体组/单变量差异/独立交付约束。只在 adfilm 里补一句“做 A/B”不足以防止 Agent 把三版当三个镜头拼起来。

首个迁移闭环宜选择此任务：证据与产品参考共用；每版独立 sequence、独立时间线与导出；保存基准版本与改动项；验收逐版核对品牌、声明、声音和 CTA。没有用户要求不自动扩成完整投放管理系统。

证据：[litv UGC 配方](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/recipe-blueprints.mjs)、[LITTO 广告规格](../cloud/src/domain/adDirection.ts)。

### 4.6 原始材料、候选材料、权威参考应分别对待

litv 用 sourceOnly 阻止原始天气底图、部分商品/角色原图槽被生成模型替代。这个约束解决的是来源真实性：一张“很像产品”的新图不能冒充用户交付的产品原图。

LITTO 已有 candidate batches、候选晋升、资产版本和 authoritativeReference，身份参考会真实进入编译。无需再建一个候选池。可补的是特定任务的输入契约：例如天气修改必须存在原图，保护构图与关键结构；商品外观以用户真实材料为准。约束只应用于要求忠实保留原物的任务，不阻止用户明确要求概念产品设计。

选角可借鉴“文字方向 → 选定身份 → 全身 → 补角度”的不确定性消除顺序，但不应强制所有角色先多付费生成脸图。已有适用参考直接复用。litv 银龄选角的 40/30/20/10 是人为评分偏好，不是经验证的审美规律，迁移时不硬编码为普适真理。

证据：[litv 扩展配方](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/extended-recipes.mjs)、[候选与晋升](../cloud/src/domain/candidates.ts)、[资产规范](../packages/skills/workflow/references/assets.md)。

### 4.7 MV：分析算法不值得替换，时间修改的闭环值得借鉴

litv `detectOnsets` 对 PCM 按窗口计算 RMS，以局部阈值挑选能量峰，用部分峰间隔中位数估算 BPM。这是轻量起音启发式，不等于稳定拍点、强拍、乐句、变速和歌词对齐；持续音、切分节奏和混音中的打击乐都会影响结果。

LITTO 当前前端已有 music-tempo 节拍分析、Basic Pitch 音符候选、能量曲线、LRC/SRT 解析、逐词/逐句转写、按 fps 量化卡点、试听校正与带歌曲 SHA-256 的分析报告。不能说 LITTO 没有音乐分析，也没有理由用更粗糙的 RMS 算法替换它。使用更复杂库同样不证明真实音乐识别一定准确；代码已标明混音最强音符未必是主唱。

更实在的差异在分析之后：

- litv 的 timing 操作同时修改镜头 seconds 与上游音频切片的 audioStart/seconds，并撤销相关任务验收。
- LITTO 的分析结果主要通过报告附件交给 Agent；musicVideo 中的 sourceStart 和 timeline 是持久规格，但 sourceStart 本身不自动裁切或发送音频。
- 因此“试听校正切点 → 更新所有对应镜头/音频区间 → 检查受影响结果 → 重做必要片段/重新导出”仍值得做成明确的业务操作，不能仅靠 Agent 重读报告。

litv 的 timing 也不能原样照搬：它要求从 0 开始、切点数与镜头数严格对应，并较宽泛地撤销音频/视频/合成验收；LITTO 要兼容有意不同步、叙事与表演交叉、同曲多段复用，以及生成长度与剪辑使用长度不同。

litv 另有给定歌词的强制对齐接口，LITTO 当前读取到的是 ASR 转写。二者的问题定义不同，可作为以后独立适配候选，不把接入一个商业端点当作完整 MV 能力。

证据：[litv 音频处理](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/production-services.mjs)、[LITTO 音乐 Worker](../apps/web/src/lib/musicWorker.ts)、[分析交接](../apps/web/src/pages/home/musicAnalysis.vue)、[MV 执行约定](../packages/skills/musicfilm/references/musicVideoDirection.md)。

### 4.8 Job 恢复：搬接口不如保留“提交”与“查询”的区别

litv 会保存远端任务信息，其制作执行器中 resume 有明确协议限制：可灵且存在 remoteId/statusUrl 才能恢复查询。Ark 保存了任务 ID，但该制作恢复入口并不普遍支持它。不能把“保存过 ID”概括为“所有模型重启恢复”。

LITTO 已有 requestId 幂等、持久化 Job。原生适配路径能凭 provider_task_id 恢复轮询；workspaceMedia 的脚本路径在服务重启后标为待核查失败，不自动重发付费请求。

可移植的是协议原则：submit 与 poll 分离，保存真正可恢复的供应商句柄。若以后补此能力，应改现有 Provider/Job 协议并逐供应商验证，不移植 litv 的第二套队列，也不把“重新运行”伪装成“继续查询”。

证据：[litv 供应商适配](https://github.com/laixi969-coder/litv/blob/dd12ed24fe1292824cd011208f23c259caedadfe/server/providers.mjs)、[LITTO Job 恢复](../cloud/src/jobs.ts)。

## 5. 哪些只能作为参考，不能直接移植

| 对象 | 不直接移植的原因 | 合适处理 |
| --- | --- | --- |
| 80 项目录整包 | 大量共享结构；文本、配方和执行语义混合 | 提炼少量任务配方，风格作为按需资料 |
| production.mjs 执行引擎 | 与 LITTO 现有领域状态、审批、Job、租户上下文重复 | 将业务前置条件接进现有链路 |
| 固定 15/20/24 秒、固定镜数 | 来源于特定方案或协议，不能推成普遍创作原则 | 按动作、交付目标、真实能力定规格 |
| 固定全局提示词拼接 | 同一上下文可能污染不相关资产与镜头 | 保留 LITTO 角色化参考及按镜编译 |
| 只凭 checklist 判定通过 | 后端能检查勾选记录，不能证明人真的看过或结果正确 | 保留证据、媒体版本及未知项 |
| 五帧检查作为完整视频 QC | 看不到全部运动、接点与声音 | 按风险采样，明确需要回放/试听的项目 |
| 均分宫格裁切 | 真实生成图可能有边框、错格和标签 | 沿用 LITTO 对实际画面与裁切坐标的检查 |
| React 页面、通用 JSON SQLite Store | 技术栈、数据隔离和对象生命周期不同 | 借鉴交互与语义，不迁入另一套应用 |
| 音乐 RMS 算法 | LITTO 已有更完整的分析入口 | 优先连接分析结果与制作修改 |

尤其不能以复制 skill 文案替代程序规则：文案能教 Agent 如何决策，不能保证重启后恢复，也不能自动维护过期审批、源素材绑定和导出分组。

## 6. 建议实施顺序：先完成一个机制闭环

### 第一批：UGC 独立变体

目标：同一真实产品材料产生可单独投放的主版与用户要求的变体，每版可追溯差异，导出不误拼接。

- 方法层：在 adfilm 下补证据台账、单变量变体与独立交付说明。
- 领域层：复用现有广告 sequence/shot/资产/剪辑；必要时只增加能表达基准版与变更项的最小元数据，不先搭通用配方引擎。
- 工具层：在现有制片工具中落实关系和导出范围；后台读回必须能区分各版。
- 验证：单独修改 CTA 不改产品身份；生成及审批只影响对应版本；三个版本得到三个实际成片文件；重开项目可恢复。

### 第二批：高风险视频试片

目标：把运动/表演可行性作为批量视频的前置条件。

- 复用现有 Take、QC 与输入指纹，明确试片验证哪些下游镜头。
- 静帧样镜通过不能替代视频风险通过；试片输入修改后旧结论过期。
- 失败不自动重试、不批量重发；用户已有适用视频时可评估复用。
- 验证：未通过试片时对应批次被拒绝；无关任务不被阻塞；试片通过后继续；换参考后重新验证。

### 第三批：MV 时间修改闭环

目标：校正音乐后，规格、切片、镜头与剪辑不会各用不同时间基准。

- 复用现有分析、musicVideo 规格和剪辑操作；以歌曲版本、区间与使用关系为依据。
- 一个明确操作计算受影响区间，更新对应规格并给出复核清单；保留旧结果。
- 区分只改剪点、替换音频、修改歌词与重生成画面，避免全部重做。
- 验证：仅移动剪点时不无条件重生成无关画面；替换歌曲能识别旧报告；重新导出与当前时间表一致。

选角分支、天气保真、对白空间锚点可作为上述机制稳定后的低成本方法补充。LITTO 已有候选池、摄影、轴线、连续性和资产规范，先补触发条件与交接，不重复建立技能体系。

## 7. 验证标准与本轮交付边界

真正的迁移验收应使用同一需求和素材，在迁移前后记录：

- 必要依赖是否能由服务端检查，绕过 UI 时是否仍成立。
- 修改一项后，受影响成果是否准确；无关成果是否保留。
- 付费提交次数、失败后重复提交次数，以及来源可追溯性。
- 用户必须作出的实质决定数量，避免用不断确认掩盖系统缺少状态。
- 真实画面、完整动作、声音及最终交付是否满足要求。

结构检查、类型检查与构建不能替代真实输出验收。本轮只完成源码链路追踪和 80 个默认配方的结构统计，未建立测试文件，未跑付费生成、浏览器端到端制作或质量盲评。

技能若后续落地，还须检查实际运行时加载：源码 `packages/skills` 经构建复制和启动时 `syncBuiltins` 同步到数据目录；存在自定义修改会保留并报告冲突，工作区同名技能也可覆盖全局技能。只改源码文件不能直接宣称正在运行的 Agent 已使用新版。验证应通过实际 `skillOperator list/read` 确认内容，不覆盖用户自定义技能。

最终取舍：保留 LITTO 的领域规格、编译、参考路由、审批证据和持久任务；吸收 litv 将具体制作风险变成显式任务依赖与交付关系的做法。先把一个专项从入口、规格、执行做到修改与交付闭环，再决定是否需要抽取共用能力。
