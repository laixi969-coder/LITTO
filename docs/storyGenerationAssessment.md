# Story 1.16.0 实测记录

本轮修改原有 `story` 技能和 `writeStoryDraft`，未增加技能入口、评审者、评分门槛或审稿请求。结论是局部事实得到修复，但故事质量仍未稳定达到 83 分，不能把程序完成标记解释为质量通过。

## 已实施的变化

- 原先的两次创作请求由“构思 → 扩写全文”改为“完整初稿 → 作者修订”。两阶段读取同一技能参考，用户限定事实优先，不按字数自动删情节。
- 作者提交原稿段落编号的替换，由程序倒序拼接；未命中的原文与分隔符保持不变。支持重复原段落，拒绝重叠、越界与清空正文的替换。此校验只验证编辑操作，不判断故事事实。
- 工具详情保留初稿与实际修改，模型上下文只接收交付版本。修订失败、截断或无效时保留初稿，明确 `complete:false`，避免用未完成的修订覆盖可用文本。
- 官方 DeepSeek Flash 请求显式使用 low 推理；高档推理修订的实测出现额度耗尽。其他接口维持非推理调用，不假定兼容。官方参数依据：[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)和[请求接口](https://api-docs.deepseek.com/api/create-chat-completion/)。参数有效不代表创作质量提高。
- 技能工作法先落实用户要求的结果，再修实际行动与状态，最后发展薄弱交锋、揭示后的行动和高潮兑现。未修改原有工作台审稿流程与评分权重。

## 实验边界

使用当前已配置的官方 `deepseek / deepseek-flash`，不将别名当作已核实的后台版本。不使用 GPT 对照，也没有独立读者盲评。报告中的分数是当前助手阅读完整正文后的主观编辑评分。

尝试了完整初稿后全文高推理修订、全文低推理修订、按段落低推理修订三种方式。高推理一篇因输出额度不足未完成；全文重写会增添临时资源和新事实。按段落替换保住了未涉及的原文，但模型仍可能遗漏受影响的后文。不能据此宣称段落方案全面优于其他方案。

最终候选包含四篇配对修订、两篇旧稿修复和一篇从零生成：

- 四篇配对稿的初稿来自本轮已经实际生成的 `causalRevision*Initial.md`，复用初稿再真实调用修订 API；不是四次全流程重跑。
- 两篇旧稿使用上一版 `finalSkill*Story.md`，只真实调用修订阶段。用于观察既有错误能否修掉，不属于新故事样本。
- `passageFreshrestaurant` 完整执行初稿和修订两次 API 请求。
- 全部保存 `brief`、初稿、完整成稿、替换、请求阶段与完成状态，未手改作品。仅保留请求参数与用量，不保存 Key 或私有推理内容。
- 本轮未实际重跑主 Agent 审稿、工作台采用和发布的完整链路；以下完成状态仅指独立写作器。

固定题目是：餐厅主厨开席前取回欠薪与署名；转运司机面对可信搭档的可疑跟踪车；暴雨仓库阻止急救物资换货并发车；渡轮船员发现失踪弟弟的身份被冒用。全部要求完整首集、不限定字数、行动引发反制、兑现本集目标，禁止用突然自白、巧合援救、万能数据或临时能力解局。完整 brief 与未编辑原稿在本地 `data/storyRuleAssessment/`；该目录被 Git 忽略，不随仓库提交。

## 正文证据与未解决的问题

### 旧稿修复确实改变的事实

《开席之前》原分项为 16400、10800、11000、5600、15200、4800，实际合计 63800，正文却写 64800。作者本次将炒锅员工的分项统一改成 12000，分项合计因此与 64800 一致。分项不是用户锁定数据，允许作者修改；这不是程序自动验算所有金额的证明。菜单仍从主角口袋转成赵总能写字、又回到主角手上，缺少实际交接；修复不全面。

《最后一辆接应车》补入方老板安排伙计把原车从修车铺送至冷库后巷，修掉原车凭空出现的缺口。但十年未联系的接应人、纸条背面的新出口及新帮手仍在需要时出现；看见对方打电话便确定其出卖证人的判断，仍未经过充分验证。原车补交接不能解决整个故事的可信度。

### 四篇配对稿

《我的名字，你的宴席》兑现了开席前工资到账，部分攻防产生阶段回报，但胜利依赖临时鉴定、商标材料、新厨房与强势客人。意向书从空白变成写满条款，缺动作；在后厨参与做菜的员工又被统称仍在外面等候。未形成充分且可信的逆转。

《白车》有绕路、核实和转运选择，证人抵达、女司机留下处理搭档问题，主体任务较清楚。但尾灯刮痕的观察视角和借车等候时长依据不足；中段反复通话，选择的真实代价偏弱。它是本批最高分，仍不是高分通过稿。

《午夜发车》最能说明局部补丁的局限：一处已经把六盒补药送上车并称二十三件全发走，后文却仍称缺药藏在消防栓附近、医院只签收二十二件，最后又送最后一件。还有相邻场面重复、驾驶与副驾驶位置冲突，以及药剂科主任在结尾变成手术执行者。替换范围合法并不能保证跨段状态一致。

《末班船》失踪弟弟让观看动机成立，但持刀对峙时发送空短信，与后文回忆兜帽男在货柜旁操作手机的时序没有接通；短信本身也不足以让船员推断手机就在船上。假证照片一会儿是弟弟、一会儿是冒用者；已发短信、解锁查看相册的手机，结尾却被说成下午四点半以后一直没开机。救出弟弟后不断追加货运、亲属、假证线索和反复收尾，稀释高潮。篇幅长本身不是扣分理由，重复和矛盾才是。

### 从零生成稿

《宴席开场前，我要拿回我的名字》用欠薪员工的配合、供应商压货及客户利益组成议价，工资在做菜前到账，名字改为合作出品。主要结果可见。但是供应商何时收到钱、卸货没有落实，菜却已经开做；已看见六点到场的张总，随后回到五点五十分装盘，未标明回叙。结尾反复安排新店、六十桌寿宴、办证和律师，主要逆转结束后仍重复说明赢了什么。法律结论是模型创作内容，未获现实核实，不能据此认定合理。

## 程序验证与结论

Server 类型检查与构建通过。内联手动校验七项通过：初稿截断、修订异常、修订截断、相同文字段落按编号准确替换、重叠拒绝、越界拒绝、正文清空拒绝。没有新增测试文件、测试封装或自动检查入口。

本地服务已重新启动，`/cloud/health` 返回 `ok:true`，3000 与 5188 服务均由 launchd 托管运行。原 story 的入口和共同工作法在源码、`data/skills` 与 `build/skills` 逐字一致；七篇正文文件与保存的工具返回文本逐字一致。

复测时 writer SHA-256 为 `7d9ce93926bacf698f5a0c462cef4f09ba08e33a8d48f9dc71bca0638491a51a`，共同工作法 SHA-256 为 `a39783a5ec0380873241a6dcdca27c2aa30b89a375cc8b855cd3cfa2aef3bd47`。复测后仅将参考文档的替换说明从“唯一定位原文”改为与实际工具一致的“原稿段落编号”，未改变生成器代码或重打分。该文档措辞修订后没有另跑付费生成。

目前可确认的是编辑操作更可追溯、失败时保稿，以及两个旧稿的特定事实改善。不能确认事实矛盾已整体解决，也不能确认精彩程度稳定提升。主要剩余问题是模型没有同步更新所有依赖同一事实的场面，同时经常用新资源、新线索代替已有条件下的有效反制。再次增加审稿调用或提示词条目并不能由本轮证据证明有效。提交这些有边界的改动，不代表完成 83 分质量目标。
