核查日期：2026-10-03。代码基线：`5a3929c`。下表保留该基线的核查快照；随后实施进展见下一节，尚未完成整套 V3。

## 本轮实施进展

### 实验 2：人工检查的操作负担（2026-10-05）

问题：「导演托管」承诺普通用户只表达意图，但 Hero/Take 门禁要求逐项人工检查。把 8 个镜头做到批准 Take，用户要付出多少操作？

方法：按「镜头制作」面板与服务端门禁逐项计数，取理想路径（每镜只检查被采用的那一个候选、不返工）。服务端强制要求：观察说明非空、关键帧 4 项和 Take 5 项全部勾选、Take 必须为每个出场资产记录结束状态；规格一改，之前的检查全部失效。

| 每个镜头 | 点击 | 手写文字 |
| --- | --- | --- |
| 关键帧检查并选为主关键帧 | 7 | 1 |
| Take 检查并批准 | 9 | 1 + 出场资产数 |

结果：按每镜平均 3 个出场资产计，8 个镜头需要 **128 次点击、40 段手写文字**。按每段文字 20 秒估算，仅检查环节就要约 17 分钟；这还不含等待生成和任何一次返工，而产出只是一支 30 到 40 秒的短片。时间是估算值，点击和文字数是按代码数出的确定值。

结论：负担主要来自手写文字，而不是点击。其中「结束状态」一项完全可以预填：每个镜头的规格里已经写了 `intendedStateDelta`，状态推导在没有实际记录时也会退回使用它，但界面目前让用户从空白手写。建议：
1. 结束状态用规格预填，用户只改与画面不符的地方；
2. 观察说明改为可选，选了缺陷类型才要求填写；
3. 「选为主关键帧」本身就代表看过画面，关键帧的 4 项勾选合并为一次确认。

做完这三项后，理想路径约为每镜 4 次点击、0 段文字，并保留人工确认这一道关。是否实施待实验 1 证明用户能走到生成画面之后再定。

### 实验 3：故事 → 拆解的结构化可靠性（2026-10-05）

方法：用 `story`、`breakdown` 技能原文作系统提示（只追加"批量评测、不追问"），经平台试用的 `agnes-2.5-pro` 对 4 个类型不同的想法各跑一次"故事 → 拆解"。每份原始输出都人工复核，排除了打分脚本的误判。只用了一个模型，没有做跨模型对比。

| 指标 | 结果 |
| --- | --- |
| 场次表 JSON 可直接解析 | **1/4（25%）**。3 份失败的原因相同：中文叙述里夹了未转义的英文双引号，如 `他没说出"我是你儿子"`。把这些引号换成中文引号后 4/4 都能解析 |
| 字段齐全 | 解析后 20/20 场全部 11 个字段齐全 |
| 场次表与正文场次数一致 | 4/4。但只有 1/4 按技能规定的「场01｜空间｜人物」格式书写标题 |
| 体量约束（短篇不超过 5 个人物、4 个场景） | 3/4。有 1 份写了 8 场、5 个场景，超出上限 |
| 拆解覆盖场次表中的人物、场景、道具 | 按名称严格匹配为 81%（57/71）。人工复核后，大多数"遗漏"是换了叫法（"壁炉白瓷钟"写成"壁炉架白瓷钟"），真正漏拆的只有 2 到 3 项 |
| 成本与耗时 | 每组"故事 + 拆解"约 1.6 万 token、17 积分、约 1 分钟。注册赠送的 200 积分约够 12 组 |

结论：低于预设的 90% 门槛，假设不成立，**不能靠技能文档约束结构化输出**。失败点很集中：一是 JSON 引号转义，二是同一实体在两步里叫法不一致。后者会让资产与场次的回链按名称对不上。建议在投入拆解确认界面和数据表之前完成：
1. 场次表改为工具调用产出：模型调用一个带 JSON Schema 的 `saveSceneList` 工具，服务端用 Zod 校验，不合格时把错误回传给模型重试，而不是解析正文里的代码块；
2. 场次表里的人物、场景、道具给稳定 id，拆解必须引用这些 id，不再按名称匹配；
3. 体量上限由校验器检查，超出时要求模型合并场次或说明理由。

**已实施（2026-10-05）：** 新增工具包 `packages/tools/sceneList`，提供 `saveSceneList`、`readSceneList`、`saveBreakdown` 三个工具。
- 场次表由工具调用产出。人物、场景、道具、服装带固定 id，场次只引用 id；服务端用 Zod 校验 id 唯一、引用存在、编号连续、每个实体至少出场一次和体量上限，不合格时逐条返回中文问题，由模型修正后重试。保存为 `场次表.json`，旧版本移入 `场次表历史/`。
- 拆解必须用 `entityId` 引用场次表实体；场次表里每个实体都要拆成资产或写进 `skipped` 并说明理由；资产类型必须和实体类别匹配；场次表版本过期时拒绝保存；出场场次由场次表自动推导。保存为 `拆解清单.json`。
- `story`、`breakdown`、`musicfilm` 三个技能改为调用工具保存，不再要求在回复里写 JSON。

**改动后复测（`agnes-2.5-flash`，免费模型，同样 4 个想法）：** 同一模型下对照两条路径。旧路径是在回复里写 JSON，新路径是工具调用、服务端校验，出错时把问题回传给模型重试，最多 3 次。新路径跑了三轮，每轮之间根据被拒原因调整校验器。

| | 旧路径 | 新路径第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | --- | --- | --- | --- |
| 场次表保存成功 | 0/4 | 4/4 | 4/4 | 4/4 |
| 拆解保存成功 | 0/4 | 3/4 | 2/4 | 4/4 |
| 场次表首次即通过 | — | 0/4 | 2/4 | 1/4 |
| 拆解首次即通过 | — | 1/4 | 0/4 | 1/4 |

三轮合计：场次表 12/12、拆解 9/12 保存成功。结论：结构化输出已从不可用变为可用，但**首次通过率仍低，依赖重试**。每多一次重试，就多一次调用的耗时和 token。

各轮之间对校验器的调整，都来自模型实际被拒的原因：场次字段改为严格模式，写成 `characters`、`location` 这类近义字段时直接报"未知的键"，不再被静默丢弃后误报"实体未出场"；`order` 改由数组位置自动编号；影调和世界设定接受关键词数组；顶层数组或对象被写成 JSON 字符串时先尝试解析；引用了不存在的实体 id 时，列出场次表里可用的 id 和名称。

剩余的常见错误是模型遗漏必填字段（如 `timeOfDay`、资产 `name`），以及 `skipped` 里的 id 格式不对。这些属于真错误，靠回传重试修正。`agnes-2.5-pro` 只测到 1 个样本（首次即通过），Pro 是否能显著提高首次通过率尚未验证。

本次实验同时发现并修复了一个计费漏洞：文本生成接口和视觉检查记录用量时，供应商被固定写成 `toonflow`，平台试用不会扣费。画布文本节点因此可以无限免费使用平台模型（`e96afa3`）。修复后实测 64,237 token 扣 67 积分，与预期一致。

### 实验 1：新用户平台免费额度（2026-10-05）

假设：首次使用必须自带 API Key 是最大的流失点。给新用户平台文本模型的试用额度后，"10 分钟内拿到第一个故事"的比例应明显上升。

- 实现：复用 cloud 的平台供应商、平台凭据和积分账本。开启后，账号模式下的新用户在模型列表里看到「平台试用」，写故事、剧本和画布文本节点都能直接用，按实际 token 从注册赠送的积分里扣（`defaultCredits`，默认 200；`creditsPer1kTokens` 默认 1）。Key 只在服务端使用。积分用完返回 402，提示接入自己的模型。图片和视频仍需自带 Key。
- 开启（推荐）：在 `cloud` 目录执行 `LITTO_TRIAL_KEY=<平台 Key> npm run trial:setup`。可选环境变量：`LITTO_TRIAL_BASE_URL`、`LITTO_TRIAL_MODEL`、`LITTO_TRIAL_CREDITS_PER_1K`；关闭用 `LITTO_TRIAL_DISABLE=1 npm run trial:setup`。脚本可重复执行，服务运行中也能执行。
- 也可以用管理员接口逐步开启：
  1. `POST /cloud/admin/providers`，`{"name":"平台 DeepSeek","adapter":"openai-compatible","baseUrl":"https://api.deepseek.com"}`
  2. `POST /cloud/admin/models`，`{"providerId":"<上一步 id>","externalModelId":"deepseek-chat","name":"DeepSeek V3","type":"text"}`
  3. `POST /cloud/admin/providers/<id>/credentials`，`{"secret":"<平台 Key>"}`
  4. `PUT /cloud/admin/system`，`{"platformTrial":{"enabled":true,"creditsPer1kTokens":1}}`
- 读数：`GET /cloud/admin/experiments/trial?since=&until=`（默认最近 7 天，不含管理员账号）。返回注册数，10 分钟和 24 小时内拿到首个回复的人数与比例，到首个回复的中位分钟数，以及首个回复走平台试用还是自带 Key。对照组是开启前同等时长的时间段。
- 判定：`rateWithin10Min` 比对照期高出 2 倍以上，且 `firstReplyVia.trial` 占多数，即证实假设，应转为正式的平台模型方案；否则说明门槛不在 Key 上，需要回头看创意入口的流程本身。
- 已知限制：以"首个成功的文本回复"近似"拿到第一个故事"；扣费在回复结束后进行，单条超长回复可能透支，下一次调用会被拦下；中位数在样本为偶数时取较大的一个；试用模型不显示上下文用量。
- 验证：隔离数据库下验证了开关、凭据缺失、取用、扣费、透支后拦截、未知模型和读数分组；隔离服务实例下以真实 HTTP 验证了管理员配置、模型列表、调用走平台凭据到达上游、额度耗尽返回 402、服务日志不含 Key。没有用真实平台 Key 跑出完整回复，首页试用提示条未在浏览器中实测。

## 结论

**当前产品未满足 V3 黄金路径和 Music Film 验收。** 已有 Toonflow 画布生成引擎、LITTO 平台与领域后端原型、自有电影/广告/连续性技能；但当前前端仍主要操作文件画布，未接通领域制片链路。

复用 Toonflow 底座本身合理；主要问题是 LITTO 的领域数据、编译、参考路由、任务和审批没有成为当前生成入口的真实业务来源。修改品牌、入口名称或补写技能无法代替这些功能。

## 技能来源与质量约束

- `canvas` 与 `workflow` 来源于 Toonflow，保留作者与上游出处；`workflow` 已有真人电影及 Seedance 提示词细则，但存在全局强制模型、硬隔离与「不做 MV 式快剪」等局部规则。
- `cinema`、`adfilm`、`continuity` 是 LITTO 自有技能，覆盖电影镜头、产品与跨镜一致性的一部分要求；目前没有完整的七岗位结构化技能协议。
- 当前 `cinema` 把生成执行交给旧 `workflow`，因此新增电影规则仍可能在执行阶段受旧规则覆盖；需要先拆清通用制片和模型专用规则的作用范围。
- 云端 `domain/skills.ts` 另有岗位逻辑与启发式分镜，`director.ts` 可选 LLM refine；这与文件技能是另一套体系。启发式固定时长/镜头补足不能作为高质量导演能力的验收证据。

电影质量不能靠更换入口名称保证。应以资产一致、可解释的摄影/光线、可信表演与物理、邻镜连续、真实输出检查作为验收对象。
