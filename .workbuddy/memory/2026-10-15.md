## 三个非显而易见的坑（重要，复用价值高）
1. **会话 Cookie 带 `Secure`，取决 `NODE_ENV==="production"`**（`cloud/src/auth.ts` `setSessionCookie`）。
   → 生产模式 + 纯 HTTP 下浏览器直接拒收 Cookie，**登录会静默失败（登录后又跳回登录页）**。
   → 结论：**必须走 HTTPS**，哪怕是自签证书。Nginx 记得传 `X-Forwarded-Proto` 且服务端 `LITTO_TRUST_PROXY=1`。
2. **生产模式无法用验证码登录**：`cloud/src/auth.ts` `requestCode()` 里 `config.production` 为真时不返回 `devCode`，且**邮件投递通道根本没接**（注释：`Mail transport is pluggable; without SMTP...`）。
   → 唯一可用的登录方式是**密码登录**（`POST /cloud/auth/password/login` → `verifyPassword`，前端登录页默认就是密码模式）。
   → 但 `setUserPassword()` **全仓库无调用方**，没有 CLI/接口能设密码 → 必须在容器内手动引导：`bun -e 'const {loginUser,setUserPassword}=await import("/app/cloud/src/auth.ts"); ...'`。
   → 管理员邮箱由 `LITTO_ADMIN_EMAILS` 决定（首位即 `is_admin`），默认值 `admin@litto.local` **必须改**成老板邮箱。
3. **`cloud/` 不在 bun workspace 里**（`workspaces` 只含 `apps/*`、`packages/*`），但 `apps/server` 直接 `import "../../../../cloud/src/embed"`。所幸 `hono` / `@hono/node-server` 已通过 apps/server 的依赖提升到根 `node_modules`，`cloud/src/sqlite.ts` 在 Bun 下走 `bun:sqlite`（无原生模块），所以 `docker build` 能跑通、且**理论上也能本地交叉构建**。

## 其他事实

- 默认 `LITTO_AUTH` 为 on（多租户）；**绝不能设 `off`**——公网裸奔，且会额外暴露 `/mcp`、`/a2a` 并关掉 SSRF 防护。

- `.dockerignore` 已排除 `**/.env`、`build`、`**/node_modules`。

## 大陆服务器部署的四个真实坑（全部实测踩过，复用价值极高）
1. **Docker bridge MTU 与路径 MTU 不匹配 ⇒ 大数据传输静默趴窝**（本次最大坑，排查耗时最久）
   - 症状：`bun install` 25 分钟只装 500M，网络 24KB/s，磁盘 30 秒涨 1M；但容器内 `fetch` 小请求 27ms 正常、`curl` 大文件 3.5MB/s 也正常。
   - 根因：`ping -M do` 实测到镜像 CDN(118.112.10.187) 的路径 MTU 只有 **1450**，而 eth0/docker0 都是 1500 → PMTU 黑洞，容器经 NAT 后 ICMP frag-needed 回不来，大包被丢。
   - 修复：`/etc/docker/daemon.json` 加 `"mtu": 1400` → 重启 docker → bridge 下 `bun install` 从「25 分钟未完成」变成 **16 秒**。
   - **这条对运行时同样致命**：LITTO 要调各家模型 API，MTU 不对会让生成请求随机挂死。
2. **github.com:443 在大陆服务器被阻断，但 codeload.github.com 通**
   - `git clone https://github.com/...` 直接 `Failed to connect ... after 134819 ms`；`codeload` 却 200/0.6s。且 github.com 的阻断是**间歇性**的（同一台机器早前测过 200/0.88s）。
   - 解法：deploy.sh 里先 `timeout 8 bash -c "echo > /dev/tcp/github.com/443"` 探测，通则 git clone，不通则下 `https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/main`。
   - **更快的兜底**：本机 `git archive HEAD | gzip -9`（22MB）通过 scp 上传，**5.3 秒跑完（4.3MB/s）**，比服务器自己从 codeload 拉（31KB/s）快 ~140 倍。跨国上传远快于服务器境内拉国际源。
3. **npm 源必须换镜像**：官方源实测 208KB/s，`registry.npmmirror.com` 3.8MB/s（18 倍），`mirrors.cloud.tencent.com/npm` 8.1MB/s（腾讯云内网，解析到 `169.254.0.3`）。
   - `bun.lock` **未硬编码 registry URL**（grep 到 0 处），所以在 repo 根写 `bunfig.toml` 的 `[install] registry=...` 即可全局生效，不必改 lockfile。
   - 腾讯云轻量/CVM 默认 `/etc/docker/daemon.json` 已带 `registry-mirrors: ["https://mirror.ccs.tencentyun.com"]`，`oven/bun:1.3.14` 33 秒拉完。
4. **`oven/bun` 镜像内没有 `curl`/`ip`**（只有 `sh`/`bun`），诊断脚本要用 `bun -e 'fetch(...)'` 代替 curl。

## 构建期踩到的另外 4 个坑（按发现顺序）
1. **`cloud/` 在 bun workspace 之外** ⇒ 干净检出必然失败两次：
   - `Could not resolve "@hono/node-server"` → 需 `cd cloud && bun install --production`。
   - `Could not resolve "@toonflow/tool-media-generation/runtime"` → **Bun 只把 workspace 包链进「各依赖方自己的」node_modules**（实测 `apps/server/node_modules/@toonflow` 有 10 项，根 `node_modules/@toonflow` 只有根自身依赖 `file`）；workspace 之外的 cloud 向上查找走到根就断了。解法：在根补齐 32 个软链（≈npm 扁平布局）。
2. **Bun 1.3.14 在 Linux 的 `--filter` 误读小驼峰目录** ⇒ `bun run --filter './packages/teams/*' build` 报 `error: ENOENT`。仓库自己的 `buildStandalone.ts` 已为 nodes/tools 手动绕过并留了注释，但 `apps/server/scripts/build.ts` 里的 teams 漏了。
3. **bind mount 盖掉镜像 chown** ⇒ 容器以 `bun`(uid/gid 1000) 运行，`/opt/litto/data` 属 root 则启动即 `EACCES ... '/app/data/settings.json.tmp-xxx'` 无限重启。需 `chown -R 1000:1000`。
4. **Ubuntu 24.04 自带 nginx 1.24 不支持独立的 `http2 on;`**（1.25.1+ 语法）⇒ `unknown directive "http2"`，改用 `listen 18443 ssl http2;`。

### 端口判定技巧（很有用）
外部探测时 **超时（7.8s）= 云安全组丢包拦截**，**快速 RST（~17ms）= 包已到主机、只是没进程监听**。
凭这个可以区分「安全组没放通」和「服务没起来」，不用去控制台反复确认。
本次即据此得出 80 早已放通（此前误判为未放通），真正缺的只有 443。

### Nginx 配置分工（避免踩坑）
- `00-litto-upgrade-map.conf` 单独放 `map $http_upgrade $connection_upgrade`——**多个 server 块重复定义 map 会直接报 `duplicate map`**，必须独立成文件且只定义一次。
- `milimili.conf`（80+443 最终态）/ `milimili.phase1.conf`（仅 80，供首次签证书）。`deploy.sh` 按「证书是否存在」决定装哪份，且证书不存在时不覆盖已有配置，避免打断线上域名。

## ⚠️ 仓库里大量源文件是 600 权限（部署时会导致容器启动即崩）
仓库（工作区）里有**大量** `600` 权限的跟踪文件——`package.json`、`apps/server/src/app.ts`、`apps/server/src/router.ts`、
`apps/server/src/agent/runtime/prompt.ts`、`apps/web/src/pages/login/index.vue`、`apps/web/src/pages/workspace/index.vue`、
`apps/web/public/favicon.svg`、若干 docs/*.md 等（历史遗留）。
- `git archive` 打包会**自动规范化成 644**，所以之前用 git archive 部署一直没暴露；
- 改用 `tar -T <(git ls-files)` 打包**会保留原始 600**，于是容器（非 root 用户 `bun`，uid 1000）启动即崩：
  `EACCES: permission denied, open '/app/build/skills/story/references/shortDramaLicense.md'`（`cp` 把 600 继承到 build/）
  修了 build/ 又冒出 `EACCES ... open '/app/package.json'`。
- 根治（Dockerfile v5）：**COPY 之后** `RUN chmod -R a+rX /app`（此时还没装依赖，开销极小）
  ＋ **构建之后** `RUN chmod -R a+rX /app/build /app/cloud`（覆盖 cp 出来的产物）。
- 教训：`git archive` 与 `tar` 对权限的语义不同，换打包方式要重新验证。

## 更新部署的正确姿势（大陆服务器）
- **不要指望服务器拉 GitHub**：`github.com:443` 常被阻断；`codeload.github.com` 虽可达但实测仅 **31KB/s**。
- **从本机推最快**：本机 `tar` 打包（22MB）→ scp/ssh 管道上传，实测 **4.3MB/s**，快约 140 倍。
- 已封装为 `update.sh`（本机运行，5 步：检查→打包→上传→同步脚本→服务器重建+自检），实测 EXIT=0。
- `deploy.sh` 新增 `--no-fetch`（等同 `LITTO_SKIP_FETCH=1`）；且 `fetch_tarball` 已改为
  **下载失败不破坏已有源码**（先下到 /tmp、解压到暂存目录、成功才替换），避免网络抖动清空线上代码。
- 打包加 `COPYFILE_DISABLE=1 tar --no-xattrs`，否则服务器的 GNU tar 会刷屏 `Ignoring unknown extended header keyword 'LIBARCHIVE.xattr.com.apple.provenance'`。
- **pkill 自匹配坑**：`pkill -f "bash /opt/litto/deploy.sh"` 会匹配到自己那条 ssh 命令并自杀（表现为 ssh 返回 255、无输出）。要写 `pkill -f "[b]ash /opt/litto/deploy.sh"`。

## ⚠️ 排查陷阱：容器内有两套数据目录，`docker exec` 会连错库
- 引擎层用 `TOONFLOW_DATA_DIR=/app/data`（`settings.json`、`workspaces/`、`skills/`、`nodes/`…）。
- cloud 层用 `LITTO_DATA_DIR=/app/data/cloud`（真正的账号库 `litto.db`、`.master.key`）。
- **`LITTO_DATA_DIR` 不是容器环境变量**，而是应用启动时 `mountCloud()` 里 `process.env.LITTO_DATA_DIR ??= join(TOONFLOW_DATA_DIR,"cloud")` 现设的进程内变量 → **`docker exec` 看不见**，于是 `config.dataDir` 落到 `process.cwd()/data` = `/app/data`，会**新建一个空的 `/app/data/litto.db`** 并且 `migrate()` 建出全套空表 → 查询全部返回 undefined，看起来像「用户不存在/没设密码」，极易误判成改密失败。
- 正确姿势：任何手工查库/引导都要显式 `docker exec -e LITTO_DATA_DIR=/app/data/cloud litto bun -e '...'`（`bootstrap-admin.ts` 里已用 `??=` 兜底，`set-admin-password.sh` 的 exec 也显式传了）。
- 附带教训：误建的空库要记得删（`/opt/litto/data/litto.db*`），别留在数据目录里混淆后续排查。

## 账号体系事实（后续改代码会用到）
- 会话有效期 **30 天**（`SESSION_TTL_MS = 30*24*3600_000`，Cookie Max-Age=2592000）；无「记住我」选项，靠 Cookie 本身长效。

- 密码用 scrypt 存储（`derivePassword`，N=32768）。

## ⚠️ 上游 Dockerfile 的安全缺陷（务必记住，排查靠这个）
**`ENV NODE_ENV=production` 写在了 `RUN bun run build:server` 之后**，而 Bun 打包器会把
`process.env.NODE_ENV === "production"` 在**构建期做常量折叠**（其它 `process.env.*` 不会被折叠，只有 NODE_ENV 是特例）。
实测产物里是 `a6={dataDir:yj,production:!1,...}` —— 硬编码 false，**运行时容器里 NODE_ENV=production 也无效**。
后果（都已实测复现）：
1. `POST /cloud/auth/request-code` 把 6 位验证码直接放进响应返回（`{"devCode":"525989"}`）→ 任何人可注册、可接管未设密码的账号。
2. 会话 Cookie 不带 `Secure`。
修复：`ENV NODE_ENV=production` 提到 build 之前，**但不能提到 `bun install` 之前**（否则 bun install 跳过 devDependencies，构建失败）。
修复后实测：request-code 返回 `{}`、Set-Cookie 带 `Secure`、登录/首页/`/cloud/auth/me` 仍 200。
`production` 共 7 处引用（auth.ts 验证码+Cookie、sso/oauth Cookie、app.ts CORS localhost 放行、sso.ts IdP 强制 https、billing.ts 支付提供方默认值），修好后全部落到更严格的一侧。
