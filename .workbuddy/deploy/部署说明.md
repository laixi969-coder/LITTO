## 二、架构

```
浏览器 ──HTTPS:18443──> Nginx(宿主机) ──HTTP──> 127.0.0.1:13000 ──> Docker 容器 litto:3000
                                                        │
                                                        └─ /opt/litto/data  (bind mount → /app/data)
```

- 容器内为 `NODE_ENV=production`；服务端自己托管前端（`build/web`），单容器即可。
- 账号体系开启（多租户 + 会话），**不可**改成 `LITTO_AUTH=off`，否则公网无鉴权裸奔。
- 容器仅监听 `127.0.0.1`，不对公网直接暴露端口；对外只经 Nginx。

## 五、对上游仓库做的 7 处适配（`deploy.sh` 每次自动重打，不会被覆盖丢失）

上游 Dockerfile 是给「有完整本地 node_modules、且能直连 GitHub/Debian/npm 官方源」的环境写的，
在**大陆干净检出**下会连续踩坑。以下改动只影响部署，不改业务逻辑：

| # | 文件 | 改动 | 不改会怎样 |
| --- | --- | --- | --- |
| 1 | `Dockerfile` | apt 源 `deb.debian.org` → `mirrors.cloud.tencent.com` | 装 ffmpeg 走 Fastly 80 端口，大陆必然超时重试，**构建卡死 8 分钟以上近乎零吞吐** |
| 2 | `Dockerfile` | `bun install --frozen-lockfile \|\| bun install` | lockfile 与 package.json 轻微漂移时直接失败 |
| 3 | `Dockerfile` | 新增 `RUN cd cloud && bun install --production` | `cloud/` 是独立包不在 workspace 内、`cloud/node_modules` 被 gitignore，干净检出必然报 `Could not resolve "@hono/node-server"` |
| 4 | `deployAdapt/linkWorkspaces.ts`（新增） | 构建期在根 `node_modules/@toonflow` 补齐 workspace 软链 | Bun 只把 workspace 链进「依赖方自己的」node_modules，workspace 之外的 `cloud/src` 解析不到 `@toonflow/*`，报 `Could not resolve: "@toonflow/tool-media-generation/runtime"` |
| 5 | `apps/server/scripts/build.ts` | `build:teams` 的 `--filter` 改为逐目录构建 | Bun 1.3.14 在 Linux 的 `--filter` 误读小驼峰目录，`packages/teams/storyboardTeam` 直接 `error: ENOENT`（仓库自己的 `buildStandalone.ts` 已为 nodes/tools 绕过，漏了 teams） |
| 6 | `bunfig.toml` + `cloud/bunfig.toml`（新增） | registry → `https://registry.npmmirror.com` | npm 官方源实测 208KB/s，镜像 3.8MB/s（18 倍） |
| 7 | `Dockerfile` | **把 `ENV NODE_ENV=production` 提到 `RUN bun run build:server` 之前** | ⚠️ **安全缺陷**：Bun 打包器会把 `process.env.NODE_ENV === "production"` 在构建期常量折叠，上游把 ENV 写在 build 之后 → 产物里硬编码成 `production:!1`，**官方镜像跑起来永远是 production:false**。后果：① `POST /cloud/auth/request-code` 直接把 6 位验证码放进响应返回（任何人可注册、可接管未设密码的账号）；② 会话 Cookie 不带 `Secure`。**注意不能提到 `bun install` 之前，否则 bun 会跳过 devDependencies 导致构建失败。** |

⚠️ 上游 Dockerfile 里 `ENV` 的位置问题属于**上游真实缺陷**，建议给上游提 issue/PR。

`deploy.sh` 里每处都带守卫判断（Dockerfile 用 `LITTO-DEPLOY-ADAPT v3` 版本标记，`build.ts` 用 `grep -q 'run build:teams'`），上游修好后会自动跳过，不会盲目覆盖。

## 六、宿主机层面的额外处理

- **Docker MTU 改为 1400**（`/etc/docker/daemon.json`）。实测到镜像 CDN 的路径 MTU 只有 1450，而 eth0/docker0 是 1500 → PMTU 黑洞，容器里大文件传输静默趴窝（`bun install` 25 分钟装不完 500MB）。
  **这条对运行时同样关键**：LITTO 要调各家模型 API，MTU 不对会让生成请求随机挂死。
- **`/opt/litto/data` 属主改为 `1000:1000`**。容器以非 root 用户 `bun`(uid 1000) 运行，bind mount 会盖掉镜像里的 chown，否则启动即 `EACCES ... settings.json.tmp-xxx` 无限重启。
- Nginx 用 `listen 18443 ssl http2;`（Ubuntu 24.04 自带 nginx 1.24 不支持独立的 `http2 on;`，那是 1.25.1+ 语法）。

### Nginx 配置文件分工

| 文件（源文件在 `/opt/litto/nginx/`） | 作用 |
| --- | --- |
| `00-litto-upgrade-map.conf` | websocket/SSE 升级头 map（独立文件，避免多 server 块重复定义报 `duplicate map`） |
| `litto.conf` | 18443 + 自签证书，兜底入口 |
| `milimili.conf` | 80（ACME + 301 跳转）+ 443（Let's Encrypt + 反代）——**最终形态** |
| `milimili.phase1.conf` | 仅 80 端口，用于首次签证书（`LITTO_TLS_PHASE=1` 时安装） |

`deploy.sh` 的规则：证书已存在 → 装 `milimili.conf`；证书不存在但已有配置 → 不动（不打断线上域名）；两者都不满足 → 装阶段一配置。
